# Worked probe examples

Three probes that run against real apps in the teksilo workspace. They are not
illustrations — each one launches its app, drives it, asserts, and exits
0 / 1 / 2. Run them; then copy the one closest to your case into `scripts/` and
edit it.

Your own probes belong **outside** this directory. Everything under
`scripts/teksilo_probe/` is generated by `cargo teksilo probe install` and a later run
will overwrite it.

| File | Drives | Copy it when you need to… |
| --- | --- | --- |
| `example_data_collections.py` | `data-collections` | reach a row a `ListView` / `TreeView` / `TableView` / `GridView` has not realised yet, or work out why a node id stopped resolving |
| `example_dialogs.py` | `dialogs-and-popovers` | assert on a dialog, message box, popover or menu — anything whose content is not in the window you started from |
| `example_rich_text.py` | `rich-text-editor` | type into something, drive an IME, undo, or read a document's text back out of the accessibility tree |

## Running them

```sh
cargo build -p data-collections -p dialogs-and-popovers -p rich-text-editor
cargo install teksilo-automation-mcp --locked     # the client half, once

python3 example_data_collections.py
python3 example_dialogs.py
python3 example_rich_text.py
```

Each takes two optional flags:

- `--binary PATH` — drive an existing binary instead of resolving one through
  `cargo metadata`. It must be a **debug** build: the automation bridge is
  `#[cfg(debug_assertions)]`, so a release build has no endpoint to attach to.
- `--keep` — leave the app running after the probe finishes, and print its pid
  and log path. For looking at what the last assertion was looking at.

Two environment variables matter, both read by `teksilo_probe.resolve`:
`TEKSILO_MCP_BIN` points at an MCP client you built yourself rather than one on
`$PATH` (`target/debug/teksilo-automation-mcp`), and `TEKSILO_APP_BIN` is the
`--binary` flag in environment form.

## Exit codes, and why there are three

- **0** — every check passed.
- **1** — the probe could not run. The binary was missing, the bridge never
  appeared, a tool call failed. *Nothing was learned about the app.*
- **2** — the probe ran cleanly and a check came back false. The behaviour under
  test is absent.

Keeping 1 and 2 apart is the whole point. A suite that reports both as "failed"
teaches its readers that a red run might just be a stale build, and then a real
regression reads the same as a forgotten `cargo build`. `Report.check` steers
towards 2; `Report.error` towards 1; never reach for `check` to record that the
probe itself broke.

## What each one is really teaching

**`example_data_collections.py` — virtualization.** A virtualized view realises
only the rows in (and slightly past) its viewport, so a row below the fold has
no widget and therefore no accessibility node at all: `tree.find` returning
`None` means *not on screen*, not *not there*. Scrolling such a row back into
view **rebuilds** it, and a rebuilt widget gets a fresh node id — so an id held
across a scroll answers `NOT_FOUND` for a row sitting right in front of you.
The probe also shows why keyboard navigation beats aiming a pointer at a node's
reported bounds: the bounds of an unrealised row are perfectly real and nothing
is painted at them, whereas teksilo scrolls the *focused* row into view, so
moving focus makes the view do the work. In this app the wheel bottoms out six
rows short of the end and one `End` gets there.

**`example_dialogs.py` — overlays are not all one thing.** A `Dialog` resolved
through `ModalPresentation::Auto` opens a real OS **window** on a backend that
supports native modals: `get_overlays` stays empty, a default `snapshot_tree`
still shows the parent, and every read has to name `window_id=`. A `Popover` is
the other shape — an in-tree overlay `get_overlays` counts. The probe asserts
focus moves into each, and comes back to the trigger. It also pins the
two-press rule (an outside press dismisses without reaching the control
beneath) to the pointer kind it actually holds for: a **direct** pointer arms
the dismissal on the press and commits on the release, while a mouse dismisses
on the press and falls through, so one mouse click does both.

**`example_rich_text.py` — reading text back.** An editor's content is not a
`value` on one node; it is `Role::TextRun` children, one per visual line,
re-segmented on every edit. Asserting on the editor node's `value` finds nothing
and looks like an empty editor. The probe walks the runs, shows a typed marker
appearing in both panes bound to the same `TextDocument`, undoes it through the
platform accelerator (`command=True`, never a literal `ctrl` — a chord declared
`Ctrl+Z` is ⌘Z on macOS and a literal Control there matches no binding *and
still reports success*), and drives an IME preedit/commit cycle, which is
observable mid-composition.

## The shape to copy

All three are laid out the same way, and staying with it is worth more than any
individual trick in them:

1. A module docstring saying what the probe proves and why it needs a live app.
2. `_bootstrap()` — put `teksilo_probe` on `sys.path`, working both from a
   consumer's `scripts/teksilo_probe/examples/` and from the framework tree.
3. Constants at the top: the app name, the markers, the pauses. A number
   buried mid-function is a number nobody will tune.
4. Small named legs, one behaviour each, taking `(session, report)`.
5. `main()` — parse, launch, `tree.wait_for` a marker (**never** `sleep`), run
   the legs, and tear down in a `finally` so a failure mid-probe still leaves
   no orphan process.

Two habits from the library that these follow, and that a new probe should:
**every non-obvious step carries a comment saying why**, because an uncommented
correct line teaches nothing and the next reader will delete it; and **a
failure message names what was on screen instead** (`tree.labels` is one line),
because "not found" without that costs a whole launch to diagnose.
